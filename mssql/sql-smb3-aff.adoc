[.lead]
This guide describes, step by step, how to deploy Microsoft SQL Server 2025 on Windows Server 2025 (Desktop Experience) with all user databases, transaction logs, TempDB and backups stored on SMB 3 continuously available (CA) shares hosted on a NetApp AFF system running ONTAP.
It covers the ONTAP storage configuration, the creation and configuration of the storage VM (SVM), the volume and share layout, the SQL Server installation, and data protection with NetApp SnapCenter.

[[introduction]]
== Introduction

Microsoft SQL Server has supported placing database files on SMB file shares since SQL Server 2012.
With SMB 3 and its continuously available (CA) shares, a file share is a fully supported, high-performance and highly available storage option for mission-critical SQL Server databases, as an alternative to block storage (iSCSI, FC or NVMe/TCP LUNs).

NetApp ONTAP implements SMB 3 natively on AFF all-flash systems.
Together with SQL Server 2025 and Windows Server 2025, this gives a storage architecture that is simple to deploy and simple to operate, that tolerates failures, and that integrates with NetApp data protection.

[[intro-audience]]
=== Purpose and audience

This document is a practical, screenshot-based deployment guide.
It is intended for:

* *Storage administrators*, who configure the ONTAP cluster, the SVM, the volumes and the SMB shares.
* *Windows and Active Directory administrators*, who prepare the Windows Server 2025 host, the service accounts and the network.
* *Database administrators*, who install and configure SQL Server 2025 and set up backup and recovery.

Basic knowledge of ONTAP System Manager, Windows Server and SQL Server administration is assumed.

[[intro-why]]
=== Why SQL Server on SMB 3 with NetApp ONTAP

[cols="1,3",options="header"]
|===
|Benefit |Description

|Simple provisioning
|There are no LUNs, igroups, MPIO, disk initialization or drive letters to manage.
A database file location is just a UNC path such as `+\\a50-sql\sql1_data+`.

|Online capacity management
|You grow (or shrink) a volume online in ONTAP, and SQL Server sees the new capacity immediately.
No Windows disk or partition operations are required, and autogrow can do it automatically.

|Nondisruptive operations
|CA shares keep SQL Server running during ONTAP takeover/giveback, nondisruptive upgrades (NDU), LIF migrations and volume moves.

|Performance and resiliency
|SMB multichannel spreads the I/O across several network paths and NICs and survives the loss of a single path.
AFF systems deliver consistently low latency.

|Storage efficiency
|Inline deduplication, compression and compaction, together with thin provisioning, reduce the physical capacity used by databases and backups.

|Integrated data protection
|ONTAP snapshots, SnapRestore, FlexClone and SnapMirror, orchestrated by NetApp SnapCenter, provide backups in seconds, restores in minutes and instant database clones.

|Flexibility
|Databases can be moved between hosts by simply attaching them on another server, without remapping storage.
The same SVM can also serve home directories, file services or other applications.
|===

[[intro-architecture]]
=== Solution overview

The solution consists of the following components:

[cols="1,3",options="header"]
|===
|Component |Role

|Windows Server 2025 host (`{host}`)
|Runs SQL Server 2025. The SQL Server binaries and system databases are on the local disk; all user databases, logs, TempDB and backups are accessed over SMB 3.

|SQL Server 2025
|Database Engine, running under a domain service account (`{svc-account}`) that has access to the SMB shares.

|Active Directory and DNS
|Authenticates the SQL Server service account and the CIFS server (Kerberos) and provides name resolution and time synchronization.

|NetApp AFF A50 HA pair
|Two controllers with shared NVMe storage. If one controller fails or is upgraded, the partner takes over its storage and network interfaces.

|Storage VM `{svm}`
|A dedicated, Active Directory-joined CIFS server with one SMB data LIF per node, hosting four NTFS volumes with CA shares.

|NetApp SnapCenter (optional)
|Creates application-consistent snapshot backups and provides restore, clone and replication.
|===

[[intro-design]]
=== Design principles

The design follows the NetApp best practices for SQL Server over SMB:

* *Separate volumes per file type.* Data, transaction log, TempDB and backups are placed on separate FlexVol volumes and shares.
Each volume can have its own size, QoS, efficiency, snapshot and replication settings.
TempDB is excluded from backups.
* *Volumes distributed across both nodes.* Data and backup volumes are on node 1, and log and TempDB volumes are on node 2, so that both controllers do useful work.
* *One SMB data LIF per node.* The host always has a direct path to the node that owns a volume, and SMB multichannel can use both paths.
* *NTFS security style and CA shares.* These are mandatory for SQL Server over SMB on ONTAP.
* *No scheduled ONTAP snapshots on the database volumes.* Backups must be application-consistent; they are created by SnapCenter.

[[intro-ca]]
=== How continuous availability works

With a standard SMB share, a controller failover closes the open file handles.
SQL Server then marks the affected databases as suspect, and they must be recovered manually.

With a CA share, ONTAP keeps the state of the open files (persistent handles) mirrored to the HA partner.
During a takeover, the SMB LIF of the failed node migrates to the partner.
The SMB 3 client on the SQL Server host reconnects automatically and reclaims its handles.
SQL Server only sees a short I/O pause of a few seconds; the databases stay online and no transactions are lost.
The same applies to planned events such as ONTAP upgrades, giveback, LIF migrations and volume moves.

[[prerequisites]]
== Prerequisites

Make sure that the following requirements are met before you start:

*NetApp ONTAP*

* The AFF HA pair is installed, and the cluster is set up and healthy.
* The CIFS (SMB) license is installed. It is included in ONTAP One.
* At least one data aggregate (local tier) exists on each node.
* Time is synchronized between the cluster and Active Directory through NTP. The maximum allowed clock skew for Kerberos is 5 minutes.
* The data network ports, broadcast domain and (optionally) VLANs for the SMB LIFs are configured.

*Active Directory and DNS*

* An Active Directory domain is available, and the DNS servers can be reached from the SVM data LIFs.
* You have an account with permission to create computer objects in the target OU, for the CIFS server.
* A dedicated domain user account (or gMSA) is available for the SQL Server Database Engine and SQL Server Agent services.

IMPORTANT: SQL Server must run under a *domain account* when its files are on an SMB share.
Built-in virtual accounts (`NT SERVICE\MSSQLSERVER`) and local accounts cannot be granted access to a remote file share.

*Windows Server*

* Windows Server 2025 (Desktop Experience) is installed, patched and joined to the domain.
* The SQL Server 2025 installation media (ISO) and a valid product key (or a free edition) are available.

*SMB requirements and restrictions for SQL Server on ONTAP*

* SMB 3.0 or later must be enabled on the SVM.
* All volumes that host CA shares must use the *NTFS* security style and must have been NTFS from the start.
* SMB Direct (RDMA) is not supported.
* ReFS is not supported. The file system is provided by ONTAP (WAFL).

[[svm]]
== Create and configure the storage VM (SVM)

Use a dedicated SVM for SQL Server.
The SVM joins Active Directory as a CIFS server and provides one SMB data LIF on each node of the HA pair.

[[svm-gui]]
=== Create the SVM with System Manager

. In System Manager, go to menu:Cluster[Storage VMs] and click *+ Add*.
+
image::sql25_smb_bp_006.png[Cluster > Storage VMs > Add,width=800]


. Enter the *Storage VM name* `{svm}`.
In *Access protocol*, select the *SMB/CIFS, NFS, S3* tab and select *Enable SMB/CIFS*.
+
image::sql25_smb_bp_007.png[Add storage VM - name and protocol,width=800]

. Enter the Active Directory information:
** *Administrator name* and *Password*: an account that can join computers to the domain
** *Server name*: `{cifs}` (the CIFS server name, which is the NetBIOS name used in the UNC paths)
** *Active Directory domain*: `{fqdn-domain}`
** *Organizational unit*: for example `CN=Computers`, or a dedicated OU for storage systems
+
Select *Encrypt data while accessing all shares of this SVM* only if your security policy requires it.
In that case, test the performance impact first.
+
. Enter the *Domains* and *Name servers* (DNS) for the SVM.
+

. Under *Network interface*, configure one data LIF on *each* node:
** Node 1: IP address `192.168.175.138`, subnet mask, home port (or broadcast domain)
** Node 2: IP address `192.168.175.139`, subnet mask, home port (or broadcast domain)
+
TIP: One LIF per node gives SQL Server a direct (local) path to each node, and it is a prerequisite for SMB multichannel and for nondisruptive failover.
Use 25 GbE or faster ports, and use the same MTU end to end.
+



. Click *Save*.
System Manager creates the SVM, the root volume, the LIFs and the DNS configuration, and it joins the CIFS server to the domain.
+
. Verify the SVM root volume (`a50_sql_root` in the lab).
It must use the *NTFS* security style.
Go to menu:Storage[Volumes], select the root volume, and click *Edit* to review its settings.
+
.SVM root volume settings (security style NTFS)
image::sql25_smb_bp_012.png[Edit SVM root volume a50_sql_root,width=800]

[[svm-cli]]
=== Equivalent ONTAP CLI

The following commands create the same configuration from the CLI.
Replace the placeholder values in angle brackets.

[source,console]
----
cluster::> vserver create -vserver a50-sql -rootvolume a50_sql_root -aggregate <aggr_node1> -rootvolume-security-style ntfs

cluster::> vserver modify -vserver a50-sql -allowed-protocols cifs

cluster::> network interface create -vserver a50-sql -lif a50-sql_smb_n1 -service-policy default-data-files -home-node <node1> -home-port <port> -address 192.168.175.138 -netmask <netmask>

cluster::> vserver services name-service dns create -vserver a50-sql -domains sapcc.stl.netapp.com -name-servers <dns1>,<dns2>

cluster::> vserver cifs create -vserver a50-sql -cifs-server A50-SQL -domain sapcc.stl.netapp.com -ou CN=Computers
----

[[svm-smb-options]]
=== Configure the SMB server options

Verify that the SMB options required for SQL Server are enabled on the SVM:

[source,console]
----
cluster::> set -privilege advanced
cluster::*> vserver cifs options show -vserver a50-sql -fields smb3-enabled,is-multichannel-enabled,is-large-mtu-enabled,copy-offload-enabled,shadowcopy-enabled

[cols="1,3",options="header"]
|===
|Option |Purpose

|`smb3-enabled`
|SMB 3.x is required for continuously available shares.

|`is-multichannel-enabled`
|SMB multichannel uses several TCP connections and network paths for higher throughput and resiliency.

|`is-large-mtu-enabled`
|Allows SMB reads and writes of up to 1 MB.

|`copy-offload-enabled`
|ODX copy offload; copies are performed inside the storage system.

|`shadowcopy-enabled`
|Remote VSS for SMB shares. Required by backup applications that use VSS for SMB shares.
|===

[[windows-prep]]
== Prepare Windows Server 2025

Perform the following steps on the SQL Server host `{host}` as a domain administrator.

. Verify that the server is joined to the domain and that the CIFS server can be resolved (see <<svm-smb-options>>).

. Make sure that the SQL Server service account exists in Active Directory, for example `{svc-account}`.
Use the same account for the Database Engine and for SQL Server Agent, or use a separate account for each.
Whichever you choose, grant each account access to all four shares.

. Test access to the shares in the security context of the service account:
+
[source,powershell]
----
PS C:\> runas /user:SAPCC\sql1admin "cmd /c dir \\a50-sql\sql1_data && echo test > \\a50-sql\sql1_data\write-test.txt && del \\a50-sql\sql1_data\write-test.txt"
----

. Open the SQL Server port in the Windows firewall:
+
[source,powershell]
----
PS C:\> New-NetFirewallRule -DisplayName "SQL Server (TCP 1433)" -Direction Inbound -Protocol TCP -LocalPort 1433 -Action Allow
----

. Verify the SMB connection to the SVM.
The dialect must be 3.x and `ContinuouslyAvailable` must be `True`:
+
[source,powershell]
----
PS C:\> dir \\a50-sql\sql1_data | Out-Null
PS C:\> Get-SmbConnection -ServerName a50-sql | Format-Table ServerName,ShareName,Dialect,ContinuouslyAvailable,Encrypted,Signed
PS C:\> Get-SmbMultichannelConnection -ServerName a50-sql
----

NOTE: By default, Windows Server 2025 requires SMB signing for all outbound SMB connections.
ONTAP supports SMB signing and negotiates it automatically.
Signing adds CPU overhead on both sides, so include it in your performance tests.
Don't disable signing without a security review.

[[snapcenter]]
== Back up SQL Server with NetApp SnapCenter

NetApp SnapCenter is a self-managed (on-premises) data protection software for applications and databases on ONTAP.
For SQL Server, it uses the *SnapCenter Plug-in for SQL Server* and the *SnapCenter Plug-in for Windows* on the database host to create *application-consistent ONTAP snapshot backups*.
SnapCenter coordinates SQL Server and ONTAP, so a backup takes seconds, no matter how large the database is, and creates no backup I/O on the host.

[[snapcenter-architecture]]
=== Architecture

The SnapCenter Server, a Windows server, manages policies, schedules, the backup catalog and role-based access.
It deploys the plug-ins to the SQL Server host and communicates with them over HTTPS (port 8145).
To create and manage snapshots, SnapRestore and FlexClone operations, SnapCenter calls the ONTAP REST API of the SVM or cluster.
SQL Server itself continues to access its files over SMB 3.

.SnapCenter architecture for SQL Server on SMB 3 shares
image::sql25_smb_bp_049.svg[NetApp SnapCenter for SQL Server on SMB 3 shares,width=1000]

[[snapcenter-workflow]]
=== How a SnapCenter backup works

. SnapCenter starts the backup job, either scheduled or on demand.
. The plug-in uses the SQL Server VDI/VSS interface to freeze the write I/O of the databases for a few seconds.
. SnapCenter creates ONTAP snapshots of the data and log volumes (`sql1_data`, `sql1_log`). No data is copied.
. The databases resume, and the backup is recorded in the SQL Server backup history (`msdb`) and in the SnapCenter catalog.
. Optional: the backup is verified with `DBCC CHECKDB` on a FlexClone mounted to a verification host.
. Optional: SnapCenter updates SnapMirror or SnapVault relationships to a secondary ONTAP system or the cloud.
. Transaction log backups run at short intervals (for example every 15 minutes) to `+\\a50-sql\sql1_backups+` and allow point-in-time recovery.

.SnapCenter backup workflow
image::sql25_smb_bp_050.svg[SnapCenter backup workflow for SQL Server,width=1000]

[[snapcenter-benefits]]
=== Major benefits

* *Backups in seconds.* A snapshot backup takes seconds for databases of any size; backup windows practically disappear.
* *No performance impact.* No data is read or copied on the host or across the network. SQL Server is quiesced for only a few seconds.
* *Restores in minutes.* SnapRestore reverts the database files to the backup state almost instantly. Combined with log backups, you can recover to any point in time or to a specific transaction.
* *Space-efficient backups.* Snapshots store only changed blocks, so you can keep many restore points with little additional capacity.
* *Instant clones.* FlexClone creates writable copies of production databases in seconds for development, test, reporting or troubleshooting. They use no additional capacity until data changes.
* *Verified backups without production load.* `DBCC CHECKDB` runs against a clone on a separate host.
* *3-2-1 protection.* Integrated SnapMirror and SnapVault replication to a secondary site or to the cloud (Cloud Volumes ONTAP, Amazon FSx for NetApp ONTAP, Azure NetApp Files) transfers only changed blocks.
* *Central management.* Policies, schedules, retention, role-based access control (RBAC), reporting and notifications for all SQL Server instances are in one place, with GUI, REST API and PowerShell.
* *Always On aware.* SnapCenter supports availability groups, including backups on the preferred replica.

[[snapcenter-steps]]
=== High-level configuration steps

. Install the SnapCenter Server on a dedicated Windows server and log in to the SnapCenter GUI.
. Under menu:Storage Systems[New], add the ONTAP cluster or the SVM `{svm}` with credentials that have the required ONTAP privileges.
. Under menu:Hosts[Add], add the SQL Server host `{host}` with the host type *Windows* and select the *Microsoft SQL Server* plug-in.
SnapCenter pushes and installs the plug-ins and discovers the instance and its databases on the SMB shares.
. Configure *Run As credentials* for the SQL Server instance, if required.
. Under menu:Settings[Policies], create a backup policy, for example:
** *Full backup and log backup*, schedule *hourly* and *daily*, retention for example 3 days
** *Log backup* every 15 minutes
** Optional: *SnapMirror/SnapVault update after backup*, and *verification* on a secondary host
. Under menu:Resources[Microsoft SQL Server], select the databases or the instance, create a *resource group*, assign the policies and schedules, and set up email notifications.
. Run a first backup on demand and check the job in menu:Monitor[Jobs].
. Test a restore (for example to an alternate database name) and a clone to make sure the end-to-end process works.

IMPORTANT: Before you deploy, check the https://imt.netapp.com/matrix/[NetApp Interoperability Matrix Tool (IMT)] to confirm that your SnapCenter version supports SQL Server 2025, Windows Server 2025, ONTAP 9.19.1 and databases on SMB shares.

[[appendix-cli]]
[appendix]
== Complete ONTAP CLI reference

The following script contains the complete storage configuration from this guide.
Replace the values in angle brackets before you run it.

[source,console]
----
# --- SVM -----------------------------------------------------------------
vserver create -vserver a50-sql -rootvolume a50_sql_root -aggregate <aggr_node1> -rootvolume-security-style ntfs
vserver modify -vserver a50-sql -allowed-protocols cifs

network interface create -vserver a50-sql -lif a50-sql_smb_n1 -service-policy default-data-files -home-node <node1> -home-port <port> -address 192.168.175.138 -netmask <netmask>
network interface create -vserver a50-sql -lif a50-sql_smb_n2 -service-policy default-data-files -home-node <node2> -home-port <port> -address 192.168.175.139 -netmask <netmask>

vserver services name-service dns create -vserver a50-sql -domains sapcc.stl.netapp.com -name-servers <dns1>,<dns2>
vserver cifs create -vserver a50-sql -cifs-server A50-SQL -domain sapcc.stl.netapp.com -ou CN=Computers

set -privilege advanced
vserver cifs options modify -vserver a50-sql -smb3-enabled true -is-multichannel-enabled true -is-large-mtu-enabled true -copy-offload-enabled true -shadowcopy-enabled true
set -privilege admin

# --- Volumes -------------------------------------------------------------
volume create -vserver a50-sql -volume sql1_data    -aggregate <aggr_node1> -size 1TB   -security-style ntfs -junction-path /sql1_data    -space-guarantee none -fractional-reserve 0 -percent-snapshot-space 5 -snapshot-policy none -autosize-mode grow -max-autosize 1.3TB
volume create -vserver a50-sql -volume sql1_log     -aggregate <aggr_node2> -size 512GB -security-style ntfs -junction-path /sql1_log     -space-guarantee none -fractional-reserve 0 -percent-snapshot-space 5 -snapshot-policy none -autosize-mode grow -max-autosize 650GB
volume create -vserver a50-sql -volume sql1_tempdb  -aggregate <aggr_node2> -size 500GB -security-style ntfs -junction-path /sql1_tempdb  -space-guarantee none -fractional-reserve 0 -percent-snapshot-space 0 -snapshot-policy none -autosize-mode grow -max-autosize 650GB
volume create -vserver a50-sql -volume sql1_backups -aggregate <aggr_node1> -size 2000GB -security-style ntfs -junction-path /sql1_backups -space-guarantee none -fractional-reserve 0 -percent-snapshot-space 5 -snapshot-policy none -autosize-mode grow -max-autosize 2600GB

# --- CA shares -----------------------------------------------------------
vserver cifs share create -vserver a50-sql -share-name sql1_data    -path /sql1_data    -share-properties oplocks,browsable,changenotify,continuously-available
vserver cifs share create -vserver a50-sql -share-name sql1_log     -path /sql1_log     -share-properties oplocks,browsable,changenotify,continuously-available
vserver cifs share create -vserver a50-sql -share-name sql1_tempdb  -path /sql1_tempdb  -share-properties oplocks,browsable,changenotify,continuously-available
vserver cifs share create -vserver a50-sql -share-name sql1_backups -path /sql1_backups -share-properties oplocks,browsable,changenotify,continuously-available

# --- Share permissions (repeat for each share) ----------------------------
vserver cifs share access-control create -vserver a50-sql -share sql1_data -user-or-group SAPCC\sql1admin -permission Full_Control
vserver cifs share access-control delete -vserver a50-sql -share sql1_data -user-or-group Everyone

# --- Verification ----------------------------------------------------------
vserver cifs show -vserver a50-sql
vserver cifs share show -vserver a50-sql -fields share-name,path,share-properties
vserver cifs session file show -vserver a50-sql -fields share,path,continuously-available
----

TIP: Distribute the volumes across the aggregates of both nodes, for example data and backups on node 1, and log and TempDB on node 2.
This uses the resources of both controllers.
